# 開発状況

## 管理画面: 主催者・プラットフォーム管理の初期縦切り

2026-07-19 時点で、管理画面の初期縦切りとして以下を実装済み。

- `apps/web-admin-organizer`
  - better-auth を使う主催者ログイン（`/sign-in`）・登録（`/sign-up`）・パスワードリセット（`/reset-password`）導線
  - イベント一覧
  - イベント詳細 / イベント設定
  - アカウント設定
- `apps/web-admin-platform`
  - better-auth を使うプラットフォーム管理者の新規登録・ログイン導線
  - `PlatformMember` によるアクセス制御（権限がない場合は `/forbidden`）
  - 主催者一覧
  - 主催者詳細
  - 月別売上一覧

主催者管理画面のイベント一覧・イベント詳細・イベント作成は `packages/api` 経由で DB を参照・更新する。
主催者の新規登録時は、メール認証なしで better-auth ユーザーを作成したあと、`organizer.account.signUp` API で主催者アカウント（`Organizer` と精算先の `Company`）を作成して `OrganizerMember` に `EDITOR` として紐づける。`organizer.account.signUp` が失敗した場合は主催者管理画面へ遷移させず、エラーを表示する。この2段階のうち後半だけ失敗するとログイン済みかつ主催者未所属の状態で残るため、`/sign-up` はログイン中の場合に主催者名だけを入力して主催者アカウントを作成できるようにし、`/forbidden` からも `/sign-up` へ戻せるようにしている。
作成された主催者は審査を経ずに有効になる（`Organizer` に審査状態のカラムを持たせていない）。審査フローが必要になった時点でスキーマとADRを追加する。
主催者イベント作成は、最初に「簡単イベント作成」と「詳細イベント作成」を選ぶ。簡単作成は1公演・一般料金前提で、基本情報・公演/券種・販売受付の3ステップで設定する。詳細作成と既存イベント編集は、基本情報・公演・席種/在庫・料金種別・販売受付/販売商品の5ステップウィザードで行う（`docs/adr/0004-event-wizard-granular-upsert-apis.md` 参照）。
公演日程は月日・開場時刻・開始時刻を分けて入力し、新規公演の初期値は月日を追加日から1週間後、開場時刻・開始時刻を18:00とする。開始時刻が開場時刻より早い場合は翌日の開始日時として保存する。
1イベントに複数公演・複数席種・複数料金種別・複数販売受付を登録でき、公演をまたぐ通し券（複数公演にまたがる販売商品）にも対応する。
在庫は公演×席種ごとに整理番号方式（`NUMBERED_ENTRY`）でのみ作成でき、指定席（座席レイアウトの選択）は未対応。
出演アーティストの登録、および保存済みの公演・料金種別・販売商品の削除は未対応（席種の無効化と販売受付のキャンセルのみ対応）。
admin 画面のアクセス制御は、主催者管理画面では DB 上の `OrganizerMember`、プラットフォーム管理画面では DB 上の `PlatformMember` で判定する。未ログインの場合は `/sign-in` へ、ログイン済みでも権限がない場合は `/forbidden` へ遷移する。
`packages/api` の `platform.*` は `platformProcedure` で `PlatformMember` の有無を必ず確認するため、ログイン済みでも管理者として登録されていないユーザーは全ルートが `FORBIDDEN` になる（`docs/adr/0009-platform-member-authorization.md` 参照）。
プラットフォーム管理者の新規登録画面は better-auth ユーザーを作るだけで、管理画面の利用権限は付与しない。開発環境の初期管理者は `bun run db:seed` が作り、本番環境は手動 INSERT で作る。ロール（`VIEWER` / `EDITOR` / `OWNER`）は定義済みだが、ロールごとの操作制限はまだ行っていない。
ローカル開発では `CORS_ORIGIN` が localhost 系の場合に `localhost:3001` / `3002` / `3003` を trusted origin として扱う。
パスワードリセットは better-auth の reset API を有効化し、現時点では開発用にリセット URL をサーバログへ出力する。

次に進める場合は、精算・プラットフォーム月次売上を `packages/api` 経由の読み取り API に置き換え、既存管理者からプラットフォーム管理者を招待する導線と、ロールごとの操作制限を追加する。
イベントウィザードについては、出演アーティスト登録、保存済み公演・料金種別・販売商品の削除、指定席（座席レイアウト）対応を次の拡張候補とする。

## ユーザー画面: イベント申し込み導線

2026-07-19 時点で、ユーザー向けの初期縦切りとして以下を実装済み。

- イベント一覧
- イベント詳細
- チケット申し込み
- チケット申し込み完了
- 新規登録 / ログイン / マイページ

イベント一覧・イベント詳細・チケット申し込み・チケット一覧は `packages/api` 経由で DB を参照・更新する。
一般ユーザーの新規登録（`/sign-up`）は、メール認証なしで better-auth ユーザーを作成する。新規登録・ログイン（`/sign-in`）のいずれもマイページ（`/my-page`）へ遷移し、未ログインでマイページを開いた場合は `/sign-in` へ戻す。
購入者向けのパスワードリセットは未対応で、`/reset-password` はプレースホルダーのまま残している。
先着販売の申し込み確定時は、外部決済プロバイダーへ接続せず、モック決済を成功扱いにして `Order` / `Payment` / `Ticket` / `TicketEntitlement` を同一トランザクションで作成する。
整理番号方式では、購入時に未販売の `InventoryUnit` を先頭から確保し、発券済みチケットに整理番号を表示する。
整理番号は席種ごとに接頭辞を設定でき、`S-1` / `A-1` のように同じ公演の別席種を見分けられる（ADR 0008 参照）。接頭辞は任意で、未設定なら数字だけを表示する。通し券では公演ごとに別の整理番号が採番される。
チケットもぎりは一般ユーザー側のチケット画面で同じチケットを2回タップしたときに実行し、`Ticket` と `TicketEntitlement` を使用済みにする。
手数料計算は ADR 0002 に合わせ、購入者負担手数料を支払予定額に加算し、主催者負担手数料は精算側の金額として分けて扱う。

次に進める場合は、複数公演・複数席種・複数料金種別、外部決済プロバイダー連携、メール認証、入場端末側のもぎり導線に広げる。
