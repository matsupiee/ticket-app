# spec の書き方

個別機能の仕様を置く。運用の全体像は [`docs/loop-engineering.md`](../loop-engineering.md) を参照する。

## ファイル

- パス: `docs/spec/NNNN-kebab-case.md`（`NNNN` は4桁連番、既存の最大値+1）
- 見出し: `# spec NNNN: <タイトル>`。番号はファイル名と一致させる。
- 追加したら [`docs/INDEX.md`](../INDEX.md) にリンクを追記する。

新規作成は [`TEMPLATE.md`](./TEMPLATE.md) をコピーする。

## ステータス

| 値 | 意味 | 実装してよいか |
| --- | --- | --- |
| `draft` | 仕様を詰めている途中。未決事項が残っている | いいえ |
| `確定` | 未決事項がゼロになり、実装に入れる | はい |
| `実装中` | 受け入れ条件を潰している最中 | はい |
| `完了` | 受け入れ条件がすべて満たされ、マージ済み | — |
| `破棄` | 作らないことにした。理由を本文に残す | いいえ |

`確定` 以降に仕様の穴が見つかったら `draft` に戻す。戻すことは失敗ではなく、想定された動きである。

## 必須セクション

`# spec` 見出しの下に、次のセクションをこの順で置く。空にしない。

### `## ステータス`

上表の値をちょうど1つ書く。

### `## 目的`

この機能が解決する課題。「何を作るか」ではなく「なぜ要るか」を書く。実装の途中で判断に迷ったとき、ここに立ち返って決める。

### `## スコープ`

この spec で作るものを箇条書きにする。

### `## 非スコープ`

**作らないもの**を明示する。ここが空だと、Agentは周辺機能まで作り込む。「今回やらない」と書いてあることが歯止めになる。

### `## 受け入れ条件`

チェックボックスで書く。1行1条件。

```md
- [ ] AC-1: 主催者が公開前イベントの一覧を開くと、下書き状態のイベントだけが表示される
- [ ] AC-2: 他主催者のイベントは、URLを直接指定しても403になる
```

条件は**観測可能な振る舞い**で書く。「正しく動く」「適切にハンドリングする」は条件ではない。そう書きたくなったら、それは仕様が決まっていない証拠なので `## 未決事項` に移す。

実装ループでは、1つ潰すごとに `- [x]` に変える。全部閉じるまでステータスを `完了` にできない（`check:spec` が落とす）。

### `## 検証方法`

各受け入れ条件をどのテストで確認するか。テスト種別の選び方は [`AGENTS.md`](../../AGENTS.md) の Test Design に従う。

```md
- AC-1: `packages/api/src/routers/organizer/event/list/handler.integration.test.ts`
- AC-2: 同上（403ケース）+ organizer の E2E
```

### `## 未決事項`

人間の判断が要る論点をチェックボックスで積む。回答が本文に反映されたら `- [x]` にする。

```md
- [x] Q-1: 下書きイベントを一覧に出すか → 出す。ステータスバッジで区別する
- [ ] Q-2: 過去公演のデフォルト表示範囲
```

**未回答（`- [ ]`）が1つでも残っていると、ステータスを `確定` 以上にできない。** これがループエンジニアリングの中心的な歯止めである。

積むものが無い場合は `- なし` と書く。空欄にはしない。

### `## 参照`

関連するADR・既存spec・外部ドキュメントへのリンク。無ければ `- なし`。
