# ループエンジニアリング

Agentに開発を任せるときの進め方を定義する。狙いは1つで、**仕様が固まっていない状態で実装を始めさせない**ことである。

## なぜ必要か

Agentは指示があれば必ず何かを書く。仕様が曖昧でも、欠けた部分を推測で埋めて完走してしまう。出来上がったものは動くしテストも通るが、意図と違う。この手戻りは、レビューで見つけた時点ですでに高くついている。

一方で、毎回人間が細かく指示を出すのでは自動化の意味がない。そこで、**仕様を固めるループ**と**実装を回すループ**を分け、両者の間に機械的なゲートを1つ置く。ゲートが閉じている間、Agentは実装に進まない。

```
[Spec Loop]                    ゲート                   [Impl Loop]
仕様を書く → 未決事項を洗う  ──→  未決事項ゼロ  ──→  実装 → verify → 受け入れ条件を潰す
   ↑              │                かつ                        │
   └──── 質問 ────┘             ステータス=確定                └── 失敗 ──┐
                                                                 ↑          │
                                                                 └──────────┘
```

## Spec Loop（仕様を固める）

成果物は `docs/spec/NNNN-*.md` 1ファイル。書き方は [`docs/spec/README.md`](./spec/README.md) を参照する。

1. Agentが仕様のドラフトを書く。ステータスは `draft`。
2. 判断できない点は**推測で埋めず**、`## 未決事項` にチェックボックスで積む。ここに積むこと自体がAgentの仕事であり、積まずに進むことが失敗である。
3. 人間が未決事項に回答し、Agentが本文に反映してチェックを閉じる。
4. 未決事項がゼロになったらステータスを `確定` にする。

未決事項が残っている限り `確定` にできない。これは `bun run check:spec` が機械的に落とす（後述）。

### 何を未決事項に積むか

- 受け入れ条件が書けない部分。「正しく動く」としか書けないなら、それは仕様が無いということである。
- 既存の振る舞いと衝突する部分。
- 複数の妥当な設計があり、選択が後の変更コストを左右する部分。

逆に、**コードとdocsを読めば答えが出ることは未決事項ではない**。まず読む。読んでも出ないものだけを積む。

### specを書かなくてよい変更

すべての変更にspecを要求するとコストが見合わない。次はspec不要とする。

- 既存specの受け入れ条件をすでに満たす範囲のバグ修正
- リファクタリング（外部から見た振る舞いが変わらないもの）
- ドキュメント・設定・依存関係の更新

判断に迷ったら書く。specは薄くてよい。

### specとADRの棲み分け

- **spec**: 個別機能が何を満たすべきか。実装完了とともに役割を終える（記録としては残す）。
- **ADR**: システム横断の設計判断と、その判断に至った背景。後から読み返される。

specを書いている途中で「これはこの機能に閉じない」と気づいたら、ADRを切って `## 参照` からリンクする。

## Impl Loop（実装を回す）

ゲートを通ったら、受け入れ条件を1つずつ潰す。

1. 受け入れ条件を1つ選ぶ。
2. テストを書く。[`AGENTS.md`](../AGENTS.md) の Test Design に従う。
3. 実装する。
4. `bun run verify` を通す。
5. 通ったら受け入れ条件のチェックを閉じ、次へ。

**ループを抜ける条件は「受け入れ条件が全部閉じたこと」であり、「Agentが終わったと思ったこと」ではない**。全部閉じたらステータスを `完了` にする。

### 途中で仕様の穴が見つかったら

実装中に「これ仕様に書いてない」が出るのは正常である。そのとき勝手に決めない。

- ステータスを `draft` に戻し、`## 未決事項` に積んで人間に聞く。
- 穴に依存しない受け入れ条件は、そのまま進めてよい。全部止める必要はない。

この差し戻しがあるからループになっている。1周で終わることを前提にしない。

## 機械ゲート

判断を人間の注意力に頼らず、落ちるようにしてある。

| ゲート | 実行タイミング | 内容 |
| --- | --- | --- |
| `bun run check:spec` | pre-push / `bun run verify` | spec の書式・ステータス整合性を検査する（詳細は下記） |
| `bun run verify` | 実装ループの各周回 | `check:spec` + `check:patterns` + lint + format:check + typecheck + unit + int をまとめて実行する |
| SessionStart hook | セッション開始時 | 進行中のspecとステータスを表示し、Agentが現在地を見失わないようにする。`.claude/settings.json`（リポジトリ共有設定）で `bun run check:spec:status` を実行している |

E2Eは実行時間が長いため `verify` に含めない。`bun test:e2e` は完了判定の直前に1回流す。

### `check:spec` が落とすもの

- 未決事項に未回答（`- [ ]`）が残ったまま、ステータスが `確定` / `実装中` / `完了` になっている
- 受け入れ条件が未達成のまま、ステータスが `完了` になっている
- 受け入れ条件がチェックボックスで書かれていない（「正しく動く」のような検証不能な条件を弾く）
- 必須セクションの欠落・順序違反・空セクション
- ファイル名の採番規則違反、見出しとファイル名の番号不一致、番号重複、`docs/spec` 直下以外への配置
- `docs/INDEX.md` にリンクが無い

## このゲートが**見ていない**こと

機械ゲートは既存のspecファイルの整合性しか見ない。次は検出できないので、人間のレビューで担保する。

- **specを1つも書かずに実装すること**。specが無ければ検査対象も無く、`verify` は緑になる。上の図の「ゲートが閉じている間は実装に進まない」は、Agentがこのルールに従う前提で成り立っている。
- **受け入れ条件が妥当かどうか**。チェックボックスで書かれているかは見るが、内容が観測可能かは見ない。「1行1条件」「`AC-1:` 接頭辞」といった書式も同様に未検査である。
- **チェックを閉じた実装が本当に条件を満たしているか**。

ゲートをすり抜ける失敗が3回起きたら、AGENTS.mdの Improve に従って検査を追加する。追加できないものはAgent Ruleとして残す。
