# ADR 0006: E2Eの決済連携は stripe-mock と自前webhookエンドポイントに分ける

## Status

Accepted

## Context

E2Eテストで「コンビニ払いは即時発券されず、入金確定後に発券される」ことを検証したい。E2Eの方針として、自分たちのAPIレスポンスとDBはモックせず実物を使う。一方で Stripe は外部サービスであり、CIから実際に叩くわけにはいかない。

コンビニ払いの検証には、決済まわりで方向の異なる2つの通信が登場する。

1. **こちら → Stripe**: 注文確定時に PaymentIntent を作成する呼び出し
2. **Stripe → こちら**: 入金が完了したことの通知（webhook）

当初 [stripe-mock](https://github.com/stripe/stripe-mock) だけで両方をまかなう案を検討したが、これはできない。stripe-mock の README は「stripe-mock is stateless」と明記しており、POSTしたデータは検証されるだけで保持されない。レスポンスは OpenAPI 仕様から生成された固定フィクスチャで、README 自身が状態遷移のテストには使えないこと、用途は基本的な健全性確認に限られることを述べている。webhook の送信機能もない。

つまり stripe-mock 単体では、コンビニ払いの PaymentIntent を作っても後から取得できず、入金待ちから入金完了への遷移も起こせず、その通知をこちらのAPIに届けることもできない。今回検証したいものが状態遷移そのものなので、検証対象が丸ごと再現できない。

実際の Stripe testmode を使う案は、CIから外部ネットワークとAPIキーが必要になり、テストの独立性と実行時間を損なうため採用しなかった。

## Decision

決済連携を通信の向きで2層に分け、それぞれ別の方法で扱う。

### こちら → Stripe: stripe-mock を使う

- PaymentIntent 作成などの外向きの呼び出しは stripe-mock に向ける。CI では stripe-mock をコンテナとして起動し、Stripe SDK の baseURL をそこに差し替える。
- 目的は**本番の呼び出しの形をCIで守ること**である。stripe-mock は OpenAPI 仕様に対してリクエストを検証するため、パラメータ名や必須項目の誤りがあればテストが落ちる。返ってくる値は固定フィクスチャなので、レスポンスの内容に依存したアサーションは書かない。
- 実キー・実ネットワークが不要になり、CIから外部依存が消える。

### Stripe → こちら: 本番と同じ webhook エンドポイントを実装し、E2Eから叩く

- 入金完了の通知を受ける webhook エンドポイントを本番用に実装する。E2Eからは、このエンドポイントに入金完了のペイロードを POST して入金を成立させる。
- 入金確定から発券（`Ticket` / `TicketEntitlement` の作成）までは**本番と同一のコードパス**を通る。DBも実物なので、検証したい振る舞いはすべて本物で確認できる。
- E2E専用の「テスト用に発券するAPI」は作らない。本番に存在しない経路を検証しても意味がないためである。

### モックしてよい範囲の線引き

- 自分たちのAPIレスポンス・DBはモックしない。
- 外部サービス（Stripe）は差し替えてよい。E2Eの「モックしない」という制約は、自分たちが書いたコードとデータに対する制約である。

## Consequences

- コンビニ払いの入金待ち・入金確定・発券という一連の遷移を、外部ネットワークなしでCIから検証できる。
- Stripe への呼び出しパラメータの誤りがCIで検出できる。ただし stripe-mock は最新APIバージョンに固定されるため、こちらが特定のAPIバージョンに固定している場合は差分を検出できない可能性がある。
- stripe-mock のレスポンスは固定値なので、「Stripeが返した金額」「Stripeが返したステータス」に依存したロジックはこのテストでは検証できない。そうしたロジックは統合テストかユニットテストで別途カバーする。
- webhook エンドポイントには署名検証が必要になるが、E2Eから正しい署名を作れるよう、署名シークレットを環境変数で差し替えられるようにする。署名検証そのものを無効化する分岐は本番コードに入れない。
- CIとローカル開発で stripe-mock を起動する手順が増える。E2Eの起動構成（DB・APIサーバー・各Webアプリ・stripe-mock）に追加する。
- stripe-mock を入れなくてもE2Eの検証内容は変わらない（webhook 側が実物であるため）。導入の価値は呼び出し形の保護に限られるので、維持コストが見合わなくなった場合は外してよい。
