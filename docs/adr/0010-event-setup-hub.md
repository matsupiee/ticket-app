# ADR 0010: イベント作成を「作成フォーム + 詳細ページのハブ」に分割する

## Status

Accepted（ADR 0004 のウィザードUI前提を置き換える）

## Context

イベント作成・編集は、基本情報・公演・席種/在庫・料金種別・販売受付を順に埋める5ステップのウィザードだった（ADR 0004）。作成モードの入口では「簡単イベント作成（3ステップ）」と「詳細イベント作成（5ステップ）」を選ばせていた。

この形には次の問題があった。

- **主催者は1回の座り作業で全部を決めきらない。** 会場と日程は先に決まるが、席割・価格・受付日程は後から決まることが多い。ウィザードは全部が揃っていることを前提にした形で、途中で離脱すると `create` を通るまでイベントが存在しない。
- **再訪コストが高い。** 「価格だけ直したい」ときにもステップを辿る必要がある。編集は何度も行う操作なのに、一本道は初回作成にしか最適化されていない。
- **順序依存は実際には末端の1本だけ。** `SaleOffer` が `InventoryPool` を要求する（ADR 0004）ため「公演・席種が先」という制約はあるが、全体が鎖のようにつながっているわけではない。
- **簡単/詳細の分岐が二重メンテを生んでいた。** ステップ定義・保存対象・専用の入力コンポーネント（`step-simple-ticketing.tsx`）が詳細作成と別に必要だった。

「基本情報だけ保存した状態」は既に安全に表現できることも分かった。`Event` に状態カラムは無く、イベントの状態は `SaleWindow` から導出される（`packages/api/src/shared/event/summarize-organizer-event.ts` の `getEventStatus`）。販売受付が1件も無いイベントは `DRAFT` になり、購入者向けの一覧・詳細にも出ない。つまりスキーマ変更なしで下書きイベントを置ける。

## Decision

- **作成フォームは基本情報と公演までで一区切りにする。** 保存すると `create` + `upsertPerformance` を実行し、イベント詳細へ遷移する。公演ゼロでも保存できる（会場・日程が未定でもイベントを起こせるようにするため）。
- **イベント詳細ページをハブにする。** 席種・在庫、料金種別、販売受付は詳細ページから個別の設定ページへ遷移して編集する。各設定ページは自分の担当分だけを保存する。
  - `/events/$eventId/edit`: 基本情報・公演（作成フォームと同じコンポーネント）
  - `/events/$eventId/seat-categories`: 席種・在庫
  - `/events/$eventId/rate-types`: 料金種別
  - `/events/$eventId/sale-windows`: 販売受付・券
- **詳細ページに「販売開始までに必要な設定」のチェックリストを置く。** ハブ型は各設定が独立するぶん「次に何をすればいいか」が失われやすいため、残件と各設定ページへの導線をここで示す。すべて揃ったらチェックリストは消える。
- **簡単作成/ 詳細作成の分岐を廃止する。** 入口の選択、`SIMPLE_WIZARD_STEPS`、`step-simple-ticketing.tsx`、`creation-mode-picker.tsx`、`APPLY_SIMPLE_CREATION_PRESET` / `RESET_DRAFT` アクションを削除した。通し券は常に選べる（`allowPassOffers` を撤去）。
- **保存APIの呼び分けはステップ番号から名前付きの保存対象に変える。** `useEventDraft` の `saveSteps([1,2])` を `save(["basic-info", "performances"])` にした。参照整合性の都合で保存順は固定なので、渡された順ではなくフック側が持つ固定順で実行する。
- **「標準価格（席種 × 料金種別）」の入力を削除する。** 標準価格はDBに保存先が無く、ウィザード内で券の初期値に使われるだけの一時値だった。ページが分かれると同一セッションで引き継げないため、入力しても捨てられるだけになる。価格は販売受付の券にのみ入力する。

## Consequences

- 公演も販売受付も無い「基本情報だけのイベント」がイベント一覧に並ぶようになる。購入者には出ないが、主催者の一覧では下書きが増える。件数が問題になったら一覧の絞り込みを検討する。
- 設定ページごとに `organizer.event.get` を呼ぶため、1つのイベントを設定しきるまでのAPI呼び出し回数はウィザードより増える。
- 席種・料金種別・販売受付は独立したページになったので、ウィザードのようにステップを disabled にして順序を強制できない。代わりに各ページの入口で前提不足（公演が無い / 席種が無い）を文章で伝える。
- 価格の入力箇所が販売受付の券だけになり、受付をまたぐと同じ価格を入力し直すことになる。イベント単位の価格表を正本として持たせる案は、`SaleOfferRate` とは別に保存先を作る判断が必要なので別ADRとする。
