# ADR 0008: 整理番号の接頭辞を席種(TicketCategory)に持たせる

## Status

Accepted

## Context

整理番号は `InventorySlot.entryNumber` が持つ整数で、`InventoryPool`（公演 × 席種）単位の連番として注文作成時に採番される（ADR 0005）。

このままだと、同じ公演にS席とA席がある場合、どちらにも「1番」が存在する。入場列で「1番の方」と呼んでも一意に定まらず、券面を見ても自分がどの列に並ぶべきか分からない。そこで席種を見分けられる接頭辞を付け、`S-1` / `A-1` と表示したい。

接頭辞の置き場所として `TicketCategory` と `SaleOffer` の2案があった。

### `SaleOffer` に持たせられない理由

**接頭辞は「番号の一意スコープ」と1:1でなければ機能しない。** 番号の一意スコープは `@@unique([inventoryPoolId, entryNumber])` が示すとおり `InventoryPool`（公演 × 席種）である。

`SaleOffer` はこのスコープと1:1にならない。1つの `InventoryPool` を複数の `SaleOffer` が参照するためである。

- `SaleOffer` は `SaleWindow` 配下にあるため、先行販売と一般販売で別の行になる。どちらも同じ在庫プールから採番する。
- 通し券の `SaleOffer` と単券の `SaleOffer` も同じ在庫プールを消費する。

この構成で `SaleOffer` に接頭辞を持たせると、**同じ番号1番に対して接頭辞が複数つきうる**。先行販売で買った1番と一般販売で買った1番が別の表記になり、入場列では別人として扱われる。逆に主催者が両方に同じ接頭辞を入力しても、それは席種単位の設定を2箇所に複製しているだけで、入力ミスによる表記揺れの余地が残る。

一方 `TicketCategory` は `InventoryPool` の一意キー `[stageId, ticketCategoryId]` の片側そのものなので、接頭辞と番号のスコープが常に一致する。

### `InventoryPool` に持たせる案

公演ごとに接頭辞を変えたい要件は現時点で無い。もぎりも入場列も公演単位で運用されるため、公演1の `A-1` と公演2の `A-1` は共存して問題ない。席種単位より細かくする理由がないため採らない。

### 通し券の整理番号

通し券（複数の `SaleOfferEntitlement` を持つ `SaleOffer`）では、公演ごとに別の `InventoryPool` から `InventorySlot` を確保する。したがって整理番号も公演ごとに独立して採番され、公演1で `A-58`、公演2で `A-142` のように異なる番号になりうる。

整理番号は入場順を決めるものであり、入場列は公演ごとに作られる。公演2の列には通し券の購入者と公演2の単券の購入者が混在するため、番号は公演2の在庫プールの連番で決まらなければならない。よって「公演ごとに独立」は正しい挙動であり、現行スキーマのままで自動的にそうなる。

全公演で同じ番号を揃える案は採らない。在庫プールをまたいで同じ番号を予約する必要があり、単券の採番と競合して採番失敗か大量の欠番を招く。得られるのは券面の見た目の揃いだけで、コストに見合わない。

通し券の購入者を優先入場させる運用は行わない。行う場合は表記を分けるのではなく `TicketCategory` そのものを分ける（通し券専用の席種と在庫プールを作る）。

### 接頭辞の変更可否

採番開始後に接頭辞を変更すると、発券済みチケットの表示も変わる。これを禁止する案もあったが、主催者の入力ミスを修正できなくなる不利益の方が大きいと判断し、変更可能とする。

## Decision

- 整理番号の接頭辞は `TicketCategory.entryNumberPrefix`（`String?`）が持つ。`SaleOffer` には持たせない。
- `null` は「接頭辞なし」を表し、従来どおり数字だけを表示する。
- `@@unique([eventId, entryNumberPrefix])` で、同じイベント内の接頭辞の重複を防ぐ。PostgreSQL は `NULL` 同士を重複とみなさないため、接頭辞なしの席種は複数あってよい。
- 接頭辞に使える文字は半角英数字の大文字1〜4文字（`/^[A-Z0-9]{1,4}$/`）とする。券面の可読性と入場列での読み上げやすさを優先する。区切り文字 `-` は接頭辞に含めず、表示時に付ける。
- `kind = RESERVED_SEAT` の席種では常に `null` にする。整理番号を採番しないため接頭辞も意味を持たない。Prisma では表現できないので、ADR 0005 の他の不変条件と同様にアプリケーション層で担保する。
- **`A-1` という整形済みの文字列はDBに保存しない。** `entryNumber` は整数のまま保持し、表示のたびに `packages/api/src/shared/entry-number.ts` の `formatEntryNumber` で組み立てる。券面・保有チケット一覧・主催者管理画面・もぎりで表記がずれないよう、組み立てはこの1箇所に集約する。
- APIレスポンスには整形済みの文字列を含め、フロントエンド側で組み立てさせない。
- 接頭辞は採番開始後も変更できる。
- 通し券の整理番号は公演ごとに独立して採番する。スキーマ・採番ロジックの変更は不要で、UI側で公演ごとに整理番号を並べて表示する。

## Consequences

- 同じ公演内で `S-1` と `A-1` が共存でき、入場列で購入者を一意に特定できるようになる。
- 採番ロジック（`InventoryPool.nextEntryNumber` の atomic な払い出し）は一切変わらない。接頭辞は表示のみに関わる属性である。
- 接頭辞を後から変更すると、発券済みチケットの表示も遡って変わる。紙の券面を配布済みの場合は表示と実物が食い違うため、主催者向けUIでは変更時に警告を出す必要がある。
- 席種を増やすたびに接頭辞の重複チェックに引っかかりうる。`@@unique([eventId, entryNumberPrefix])` 違反はAPI層で「この接頭辞は既に使われています」と返す必要がある。
- 通し券の購入者は公演ごとに異なる番号を持つため、保有チケット一覧では「1つの通し券に複数の整理番号がぶら下がる」表示になる。1枚のチケットに1つの番号を出す前提のUIは作らない。
- イベント作成ウィザードの席種ステップに接頭辞の入力欄が増える。任意入力とし、未入力なら `null` を保存する。
- 現時点で API 層の handler は空であり（ADR 0007 のリライト待ち）、入力バリデーション・レスポンスへの反映はリライト時に実装する。本ADRはその際の前提を固定するものである。
