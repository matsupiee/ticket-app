# Agent Rules

Agentが繰り返した失敗のうち、**機械的に検出できないもの**をルールとして残す場所。

[`AGENTS.md`](../AGENTS.md) の Improve から昇格してくる。ルールの分類と昇格先の一覧は AGENTS.md の「知識の置き場所」を参照する。

## ここに書くもの

次の3つをすべて満たすものだけを書く。

1. AGENTS.md の Improve が定める回数を満たして繰り返された失敗である
2. linter・型・テスト・`scripts/check-*.ts` のいずれでも検出できない
3. `docs/coding-pattern/` にも `AGENTS.md` 本体にも収まらない

典型的には、「判断そのものが誤りやすい」類のものが残る。コードの書き方（→ coding-pattern）でも、作業の進め方（→ AGENTS.md）でもないものである。

### 繰り返しをどう数えるか

**リポジトリ内に発生回数の台帳は作らない。** GitHubのレビュー履歴（PRコメント・レビュー）が正本であり、そこを検索して根拠を集める。ルールを書くときは、根拠になるPRやコメントへのリンクを `症状` に列挙する。**リンクを3件挙げられないものは、まだここに書く段階ではない。**

こうしているのは、回数を数えるためだけに時系列ログを持つと、それ自体が読まれない記録の山になるためである（AGENTS.md「知識の置き場所」を参照）。

## ここに書かないもの

- **機械的に検出できるもの**。ルールとして書くのではなく、検査を追加する。ルール化は最終手段である。
- **根拠を3件挙げられないこと**。まず様子を見る。ここが「気になったこと」の置き場になると、量に埋もれて全部読まれなくなる。
- **個別機能の仕様**。`docs/spec/` に書く。
- **設計判断とその背景**。`docs/adr/` に書く。

## 書式

1ルール1見出し。番号は連番で採番する。

```md
## AR-001: <命令形の短いルール>

- 症状: <実際に起きた失敗と、根拠になるPR・レビューコメントへのリンク3件以上>
- ルール: <どうすべきか>
- 機械化できない理由: <なぜ検査にできないか。ここが書けないなら検査を書くべき>
```

「機械化できない理由」を必須にしているのは、**ルールを追加する前に検査を検討させる**ためである。書けないものはここに来る資格がない。

## 棚卸し

- ルールが20件を超えたら、機械化できるものが混ざっている合図とみなして棚卸しする。
- 検査に置き換えられたルールは廃止する。検査とルールの両方を残さない。

役目を終えたルールは、**見出しだけを1行残して本文を削る**。

```md
## AR-003: （廃止: scripts/check-spec.ts の spec/open-questions に置き換え）
```

番号を再利用しないためである。過去のレビューコメントが指す `AR-003` と、現在の `AR-003` が別物になると、指摘が追えなくなる。

**本文を持つルールが増え続けている状態は、この仕組みが機能していないことを意味する。** 減っていくのが正常である。

## 検査

ルールが1件でも入った時点で、書式（`AR-NNN` の採番、3項目の有無、根拠リンク3件以上）を `scripts/check-*.ts` で検査する。これらはすべて決定論的に判定できるため、AGENTS.md の「決定論的に検出できるものは検査にする」に従う。0件のうちは検査対象が無いので書かない。
